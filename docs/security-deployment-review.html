Changed since the 30 July review — read this before the rest. The API was its own website then, and this document said so: the Web held no connection string, and compromise of the Web tier yielded a session rather than database access. On 2 August 2026 the API became a library hosted inside the website. The website now holds the connection string and is the data-access boundary, so that mitigation no longer exists and the Web tier must be assessed as a data-tier component. What replaced it is InternalApiGuard (§08): /api/v1 is refused from anywhere but the machine itself, so the surface that was network-reachable is now loopback-only. The Worker is unchanged — same data path, no inbound port.

04

Data flows and trust boundaries

Sign-in sequence — KocEnvironment mode

1.  Browser  → Web    GET /            (IIS has already completed Kerberos/NTLM)
2.  Web             reads the Windows principal from the request
3.  Web      → self  POST /api/v1/auth/exchange   (loopback; same process since 2 Aug 2026)
                     body:    { userId, displayName, email }
                     headers: X-Koc-Exchange     = base64(HMACSHA256(key, "userId|unixSeconds"))
                              X-Koc-Exchange-At  = unixSeconds
4.  Surface         verifies HMAC, rejects if clock skew > 5 minutes
5.  Surface         provisions the user if unseen; reads roles from the database
6.  Surface  → Web   200 { accessToken (JWT HS256, 8 h), expiresUtc, roles }
7.  Web             issues koc.auth cookie, expiry pinned to the token's
8.  Web      → self  every later call: Authorization: Bearer <token>

Step 4 is the load-bearing control. Without a valid HMAC no token is issued for any user id, and anyone holding the key can mint an assertion for any employee — which is why it is a Tier-0 secret in §06. Note what the merge changed: this exchange no longer crosses the network, so it is no longer interceptable in transit, but it is also no longer a boundary between two processes. The key now protects a call the host makes to itself.

The signing key is written to disk in plain text by first-run setup. Anyone who can read setup.json can forge an access token for any user, including a Platform Admin. For production, supply Auth:TokenSigningKey from the KOC secret store through configuration instead of completing the setup wizard, and restrict the file's ACL to the application-pool identity. There is no key-rotation mechanism in the application: rotating means changing the value on both hosts and restarting, which invalidates every live session.

07

Authorization model

Authorization is owned entirely by the application database and re-evaluated per request. Two deliberately separate notions:

Position

Employee · Team Leader · Manager · DCEO · CEO. Derived from the primary org-unit membership — the reporting line. Never granted by hand; an administrator cannot assign one.

Function role

Platform Admin · Competition Admin · Learning Admin · Auditor. Granted in the RBAC console. Cannot contain a position; the service rejects the attempt.

PolicySatisfied by
RequireEmployeeAny position
RequireSupervisorTeam Leader, Manager, DCEO, CEO, or Platform Admin
RequirePlatformAdminPlatform Admin
RequireCompetitionAdminCompetition Admin or Platform Admin
RequireLearningAdminLearning Admin or Platform Admin
RequireAuditorAuditor or Platform Admin

External role claims are discarded. If an identity provider asserts Platform Admin, the application ignores the assertion and uses its own record — otherwise whoever administers the directory could grant themselves the platform. Enforced in KocUserDirectory; covered by an integration test.

Object-level controls

  • Visibility scope — datasets, competitions, discussions and tracks each carry Team / Group / Directorate / Company, resolved against the requester's org membership. Enforced in the service layer, not at the endpoint, because six routes can reach a competition and gating only the browse list would leave five open.
  • Data classification — Confidential and Restricted dataset downloads require the owner or a Platform Admin.
  • Answer keys — stored Restricted, never returned by any endpoint; scoring is server-side.
  • Model inference — a non-production model version is usable only by its owner or a Platform Admin; promotion requires two approvals from different people, and the registrant cannot approve their own.
  • Last-admin guard — the final Platform Admin cannot be demoted, so the console cannot lock everyone out.
08

Anonymous attack surface

Sixteen API endpoints are reachable without authentication — the complete set, enumerated from source rather than recalled. Everything else requires a valid bearer token.

/api/v1 is refused from off-machine before authentication is even considered. Since the surface moved in-process, InternalApiGuard answers 404, not 403, to any request that did not originate on this host — a refusal would tell a prober there is something to find. The leaderboard hub is deliberately exempt: KOC Studio connects to it from a workstation, so it is the one part with a genuine remote caller. The sixteen anonymous endpoints below are therefore reachable from the host itself; from a workstation they do not exist.

Two settings govern this, and one deployment turns it off. Platform:InternalPort opens the loopback listener; IIS in-process hosting ignores UseUrls, so it must be 0 there, and the surface is then mapped on the site's own listener with Platform:InternalApiOnly=false — which makes it publicly reachable. That is the configuration of the public demo host (§11); a KOC intranet deployment should keep the guard on.

Anonymous still means scoped. A caller with no account resolves to no org membership, so the visibility evaluator yields company-wide rows only. Team- and Group-scoped discussions are unreachable anonymously — covered by an integration test (Opening the community up does not open the narrower discussions).

The colleague-directory search behind @mentions (/community/mention-candidates) is not anonymous: reading a post is open, enumerating who works at KOC is not.

Decision requiring sign-off

The community is readable without an account, including colleagues' real names.

Learning material, discussions, thread attachments, individual and team leaderboards, the badge wall and the activity feed are all served to unauthenticated callers with real display names and user ids. An earlier build masked names to initials for signed-out visitors; the masking was removed on 30 July 2026 at the product owner's direction, on the reasoning that a visitor should see the same company data any employee sees.

DeploymentReachable byAssessment
KOC intranet (IIS, Windows auth) Anyone on the KOC network Low — the network is the boundary. "Anonymous" here means an employee who has not yet completed the sign-in exchange, not a stranger.
Published to the public internet Anyone, including search-engine crawlers Requires sign-off — employee names, standings, activity, and any file attached to a company-scope discussion become publicly readable and indexable.

Recommendation. For an intranet deployment, no change. If the platform is ever published beyond the KOC network, three options exist in increasing order of effort:

  1. Accept it, and keep the site behind the corporate network boundary.
  2. Restore name masking for unauthenticated callers — removed in commit 0035f23, reinstatable in under an hour.
  3. Require authentication for the community entirely, leaving only the learning catalogue open.

This document does not assume an answer. It is recorded because it is the one decision here with a material external-exposure consequence.

13

Assurance and scope of this document

The behaviours above are covered by an automated suite of 513 tests run against the application in its real configuration — a live HTTP host and a real database — rather than against mocks. Security-relevant cases include:

  • Roles asserted by an external identity provider are ignored in favour of the database.
  • A position cannot be granted as a function role.
  • The last Platform Admin cannot be demoted.
  • Opening the community to anonymous readers does not expose narrower-scoped discussions.
  • The colleague directory is not searchable without an account.
  • Confidential and Restricted datasets refuse download to anyone but the owner or an admin.
  • Disabling a competition category hides it from every route reaching a competition, not just the browse list.
  • A model version cannot be approved by the person who registered it, and needs two distinct approvers.

What this document is not. It describes the controls implemented in the application, established by reading its source. It is not an independent security assessment, a threat model, or a penetration test, and it should not be relied on as a substitute for any of those. Rows marked Deployment are the hosting engineer's to confirm — the software makes no claim about them.
